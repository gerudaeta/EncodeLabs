# Bonus questions

## 1. What would you use a cache for in a conversational inbox?

For the reads that every operator repeats constantly and that change only on known events: the conversation list with its unread counts and previews, which every open tab refetches on each realtime notification. This project already does that with an in-memory `HybridCache` for the first page, evicted on every event that changes it (inbound message, reply, mark-read) *before* clients are notified, with a short TTL as a safety net ([ADR-005](adr/ADR-005-conversation-list-cache.md)). With several API instances I would add Redis as the `HybridCache` L2 so all instances share and invalidate the same entries, and reuse it as the SignalR backplane so a notification reaches operators connected to any instance. Other good fits: a short-TTL key per Telegram `update_id` to drop webhook redeliveries before they reach the database, contact profile data (names, avatars) that rarely changes, and rate-limit counters for outgoing messages to respect Telegram's limits. I would not cache message history itself: it is append-only, already served by an indexed keyset query, and a stale thread is worse than a slightly slower one.

## 2. How would you handle multimedia file traffic?

Keep the binary data out of the message path. The webhook and RabbitMQ would carry only metadata (Telegram `file_id`, type, size, MIME type, caption), so queues and the database stay small and fast. A separate consumer on its own queue downloads the file through the Bot API (`getFile`, which is limited to 20 MB per download), validates type and size, optionally scans it and generates thumbnails, and stores it in object storage (S3 or MinIO in Compose) under a content hash to avoid duplicates. The database keeps only the object key and metadata, and the inbox loads files through short-lived signed URLs (behind a CDN in production) instead of streaming them through the API. For outgoing media the operator uploads directly to object storage with a pre-signed URL, and the backend sends it to Telegram, reusing the returned `file_id` for later sends so the same file is not uploaded twice. Retries, dead-lettering and per-file status (pending, ready, failed) follow the same pattern already used for text messages, so a slow or failed download never blocks text conversations.
