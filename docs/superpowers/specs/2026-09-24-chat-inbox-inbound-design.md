# Chat Inbox: Inbound Telegram Slice

## Purpose and boundary

Make the first functional, inspectable inbound path: one Telegram bot sends text updates through ngrok to the .NET API; the API validates and durably enqueues them; a background consumer in that same host persists conversations and messages in PostgreSQL; read-only HTTP queries expose the result. This extends the buildable shells on `develop` (`4037f31`) and follows [ADR-001](../../adr/ADR-001-database.md) and [ADR-003](../../adr/ADR-003-webhook-rabbitmq.md). The local challenge brief is not present in this checkout, so this design uses the approved PR2 scope rather than inventing further requirements.

This PR does **not** add operator authentication, media, edits, outbound replies, SignalR, or Angular inbox behavior. The unauthenticated read API is for local verification only; it must not be represented as a production-safe public inbox. In PR2, change the API host-port mapping from `8080:8080` to `127.0.0.1:8080:8080`; ngrok still reaches `api:8080` on the private Compose network. Apply an ngrok Traffic Policy that denies every public request except `POST /webhooks/telegram`. Together, these controls keep the GET routes off LAN interfaces and the public tunnel until an authorization design exists. ngrok documents [path-based request rules and deny actions](https://ngrok.com/use-cases/api-gateway).

## Components and request contracts

- `ChatInbox.Api` remains the only executable host and composition root. Thin Minimal API handlers validate transport details and call application use cases. `Application` owns inbound processing and query contracts; `Infrastructure` owns Telegram, RabbitMQ, and PostgreSQL adapters; `Domain` stays framework-free. No empty abstractions are required.
- `POST /webhooks/telegram` accepts Telegram JSON `Update` with a single `update_id`. Require `X-Telegram-Bot-Api-Secret-Token` and compare its configured value without leaking it; missing/wrong token returns `401` before publishing. Enforce `application/json`, a 64 KiB request-body limit, and parseable `update_id`; malformed requests return `400` (oversize returns `413`). Do not log tokens or full message bodies.
- Only `message` updates with nonempty `message.text` of at most 4,096 Unicode characters are in scope. Other authenticated, well-formed update types are intentionally ignored with `200` and a metric; they must not create a conversation. `allowed_updates=["message"]` is set during registration, but Telegram notes that older, disallowed updates can still arrive temporarily. Do not treat unsupported updates as errors that trigger endless Telegram retries. Over-limit text returns `400`; do not silently truncate. Telegram's [Message contract](https://core.telegram.org/bots/api#message) gives the 4,096-character text bound.
- For an in-scope update, publish a versioned envelope containing `update_id`, Telegram `chat.id`, `message.message_id`, `message.date`, text, and available sender/display fields. Keep the transport payload minimal and never include the bot token or webhook secret. Return `200` only after a routable, persistent RabbitMQ publication receives a positive publisher confirm; `5xx` on broker failure, negative/absent confirm, return-as-unroutable, or timeout. An uncertain publish can later be redelivered; idempotency handles it.
- `GET /api/conversations?limit=<n>&before=<cursor>` returns a newest-activity-first page with `id`, Telegram chat ID, display name, last-message timestamp, and last-message preview. `GET /api/conversations/{id}/messages?limit=<n>&before=<cursor>` selects the newest page of message `id`, Telegram message ID, direction (`inbound`), text, and sent timestamp, then renders that page in chronological order. Both default to 50 rows, permit 1–100, and return opaque `(timestamp, id)` keyset cursors; `before` means older than the oldest returned item, with a stable `id` tie-break. Return `400` for invalid cursors/limits and `404` for unknown conversation. Neither endpoint sends messages or mutates state. These routes are intentionally local-only pending auth.

## Persistence and idempotency

PostgreSQL is authoritative. Migrations create `conversations` (`id` UUID PK, `telegram_chat_id` bigint UNIQUE, display fields, `last_message_at`), `messages` (`id` UUID PK, `conversation_id` FK, `telegram_message_id` bigint, `telegram_update_id` bigint, `text`, `sent_at`, `direction`, unique `(conversation_id, telegram_message_id)` and unique `telegram_update_id`), and `processed_updates` (`update_id` bigint PK, `processed_at`). Add indexes for `(last_message_at DESC, id DESC)` and `(conversation_id, sent_at, id)` query paths. Telegram chat/message/update IDs must not be treated as 32-bit values.

One database transaction inserts the processed marker, upserts the conversation by Telegram chat ID, inserts the message, and updates conversation summary. Concurrent duplicate deliveries race on the unique update ID; one transaction wins and the other observes the committed duplicate as success, without another message. A database failure rolls back all of these changes. Consumer acknowledgement occurs only after the transaction commits (or after a duplicate's previously committed transaction is confirmed). A crash after commit but before acknowledgement therefore redelivers and safely deduplicates. This is **at-least-once delivery with idempotent persistence**, not end-to-end exactly-once delivery. Preserve Telegram `message.date` separately from processing time; late/out-of-order updates must not move `last_message_at` backward. Do not assume `update_id` is gap-free: Telegram may choose a random next ID after a long idle period.

## RabbitMQ topology and failure behavior

Declare one durable direct exchange, one durable inbound quorum queue, and a binding with a fixed routing key at startup; publish with persistent delivery mode, `mandatory` routing, and publisher confirms. Treat `basic.return` as failure even if a confirm follows. The webhook's HTTP success means broker acceptance, **not** database persistence. Confirm and consumer acknowledgement are distinct RabbitMQ mechanisms ([RabbitMQ confirms](https://www.rabbitmq.com/docs/confirms)).

Pin RabbitMQ to a tested 4.3 image (do not rely on floating `rabbitmq:4-management` semantics). Consume with manual acknowledgements, prefetch 1, and one scoped database transaction per delivery. Configure the inbound quorum queue with delivery limit 5, delayed retry for `all` returns (1 s minimum, 30 s maximum), and a durable dead-letter exchange/queue; use `basic.reject(requeue=true)` for transient persistence failures so the failure counts toward the limit, and `basic.reject(requeue=false)` for malformed envelopes. Never positively ack these failures. RabbitMQ 4.3 documents [quorum delayed retry, delivery counts, and dead-letter limits](https://www.rabbitmq.com/docs/quorum-queues); test the actual pinned image's disposition behavior before claiming the retry bound. A consumer crash leaves unacked deliveries available for redelivery. Log update IDs and failure categories (not message text); expose queue depth/dead-letter count and processing failures for local diagnosis. A dead-lettered update is not counted as persisted success.

## Automatic webhook registration and secrets

After a valid local `.env`, plain `docker compose up` must start the five-service stack, discover ngrok's HTTPS public URL, and call Telegram `setWebhook` automatically; no copied URL or manual `setWebhook` command is part of the happy path. An API-hosted registration service waits for the local ngrok agent API, reads the v3 `endpoints` list's `url`, selects exactly one HTTPS endpoint forwarding to this API, appends `/webhooks/telegram`, and calls `setWebhook` with `secret_token` and `allowed_updates=["message"]`. If the agent reports zero or ambiguous candidates, fail registration visibly rather than guessing. The configured v3 `endpoints:` agent API is queried privately at `http://ngrok:4040/api/endpoints` (not the API container's localhost); candidates must have HTTPS `url` and `upstream.url` equal to `http://api:8080`.

The ngrok agent's default inspection API binds `127.0.0.1:4040`, which another container cannot reach. Use a checked-in ngrok v3 agent configuration with `agent.web_addr` bound to the **private Compose network** (for example `0.0.0.0:4040`) and restrictive `agent.web_allow_hosts` for the intended Compose hostname. Do not publish port 4040 to the host or tunnel it to the internet. The official [ngrok v3 config reference](https://ngrok.com/docs/gateway/agent/config/v3) documents both fields; verify the selected Docker image accepts the exact config and that `ngrok:4040` returns one correct HTTPS `url` in integration testing. This agent API is a discovery mechanism, not a Telegram webhook receiver.

Start registration only after the webhook endpoint and required intake dependencies are ready. Retry transient ngrok/Telegram failures with bounded exponential backoff and clear unhealthy/not-ready status; do not silently declare the integration ready. On every API startup, call `setWebhook` with the discovered URL and configured secret even if `getWebhookInfo.url` already matches: Telegram does not expose the configured secret for comparison. Reconcile again when the tunnel URL changes during a running process; use `getWebhookInfo` to observe URL, pending count, and delivery errors. `setWebhook` uses `drop_pending_updates=false`; startup must not discard Telegram backlog. Do not delete the webhook on normal process shutdown, because Telegram may retry while the stack restarts. An ngrok URL change can temporarily prevent delivery; surface last registration error and Telegram pending-update count where available. Telegram documents HTTPS POST retries on non-2xx, `setWebhook`, `getWebhookInfo`, `secret_token`, and `allowed_updates` in its [Bot API](https://core.telegram.org/bots/api).

Configuration supplies the Telegram bot token, a distinct random webhook secret (Telegram's allowed characters and length), PostgreSQL and RabbitMQ credentials, and ngrok authtoken through ignored `.env`/container environment; `.env.example` contains placeholders only. Fail configuration validation without printing values. Use typed, validated options and a TLS-verified Telegram API client. Keep credentials out of source, logs, queue payloads, and test snapshots. Automated tests use fakes/local containers and must **not** require a real Telegram bot token or ngrok account.

## Verification and delivery boundary

Acceptance is observable in these cases:

1. With valid local credentials, `docker compose up` discovers the tunnel and `getWebhookInfo.url` equals its HTTPS URL plus `/webhooks/telegram`; a real webhook carrying the configured secret is accepted, while one without it is rejected. Registration does not drop backlog. Without credentials, unit/component tests still run using fakes.
2. Missing/wrong secret and malformed/oversize payloads never reach RabbitMQ. A valid text update gets HTTP success only after positive broker confirmation; an unroutable or unconfirmed publish gets a retryable failure.
3. A confirmed update becomes one conversation and one message visible through both GET routes. Repeating the same `update_id`, including across consumer restart or concurrent deliveries, creates no second message. Late messages do not regress conversation ordering.
4. A database outage leaves the delivery unacknowledged/retriable; recovery before the retry limit persists it once. A poison or exhausted delivery appears in the dead-letter destination with diagnostic visibility and needs explicit replay after recovery. Query pagination stays stable across equal timestamps.
5. The ngrok inspection API is reachable only inside Compose. Verify that the GET routes work through `127.0.0.1:8080`, cannot be reached through a LAN address or the public ngrok tunnel, and that ngrok still forwards webhook POSTs to `api:8080`. Secrets and message bodies are absent from routine logs.

Implement unit tests for mapping, validation, idempotency decisions, query cursors, registration selection/retry, and failure classification; API/component tests for response semantics; PostgreSQL/RabbitMQ integration tests for transaction rollback, duplicate races, confirms/returns, ack timing, retry/dead-letter flow; and an optional credentialed Compose/Telegram smoke test. Report each evidence tier separately. Passing fake-provider tests, independent builds, or container health checks do not prove live Telegram delivery. A real bot token and ngrok authtoken are needed only for the optional live smoke test, not automated CI.

## Tradeoffs, risks, and next increments

The queue decouples HTTP intake from database latency but adds routing, confirms, retries, and operational visibility. Direct database persistence would be simpler but contradicts ADR-003 and couples Telegram retries to database outages. A separate Worker deployment isolates resources but is unnecessary for this first slice; a same-host consumer needs bounded concurrency so it cannot starve the API. PostgreSQL unique constraints, rather than in-memory deduplication, survive restarts and concurrent consumers. The local ngrok agent API avoids manual registration but introduces startup and tunnel-lifecycle coupling; wrong endpoint selection must fail closed.

This design is the PR2 boundary. A later increment can add authenticated operator reads, SignalR reconciliation signals, outbound Telegram replies, and Angular UI. No part of this PR claims those flows are working. The pinned RabbitMQ retry behavior and ngrok container discovery/policy need integration proof; if the selected images do not support the specified contracts, stop and revise the design rather than silently dropping automatic registration or bounded retries.
